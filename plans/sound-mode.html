Sound Mode — Implementation Plan

Repo: tamofishi. Saved in tamofishi/plans/, matching where the Tracked plan docs live.

Context

Tamofishi is currently silent — there's no <audio> element, no sound file, no audio-related code anywhere in src/. The task asks for a way to enable sound, which this plan reads as: an opt-in toggle (default off, since an aquarium tab playing sound unprompted on every reload would be an unwelcome surprise) that, once on, plays small sound effects for a handful of existing tank events. This is a plan for review, not a built feature — nothing here is implemented yet.

Why opt-in, not opt-out

Tamofishi is the kind of app people leave open in a background tab for hours (per its own lastFeedAt/mortality mechanics, it's explicitly designed to keep running unattended). Autoplaying audio on load would also likely be blocked by browsers' autoplay policies until a user gesture occurs anyway, so an explicit "turn sound on" action is both the friendlier choice and the one that actually works reliably across browsers.

Sound events

Mapped to code that already exists today — no new game-state hooks required, only a call at each existing site:

EventTrigger siteSound
FeedingfeedAt() in game.jsShort "plink" as flakes hit the water
Fish/shrimp eats foodfed() / the shrimp-eaten branch in fish.jsSmall "gulp"
Fish diesstartDying() in fish.jsSoft descending tone — this is an ambient sim, not a game-over sting, so it should read as gentle, not alarming
Murder mode killhandleTap()'s murder-cursor branch in game.jsA distinct "snip"/pop, since this is a deliberate user action, not passive simulation — worth being satisfying
New offspring spawnthe reproduction branch in fish.js' updateTiny "bloop"
Toggling sound onthe new settings toggle itselfOne confirmation chime, so turning it on has immediate, obvious feedback

Bubble-popping and duckweed-related events are deliberately left out of v1 — bubbles and duckweed shadows are ambient/frequent enough that sound on every one would be noisy rather than pleasant. Can be revisited once the above lands and it's clear whether more coverage is wanted.

Asset format & loading

Short WAV or OGG clips (a handful of frames of runtime cost each, no streaming needed) under a new assets/sfx/ directory, matching the existing top-level assets/ convention. Loaded once at startup into a small lookup object (new Audio(path) per clip, cloned via .cloneNode() on each play so overlapping triggers — e.g. two fish eating in the same frame — don't cut each other off).

Sourcing the actual clips is out of scope for this plan — needs either royalty-free assets (e.g. freesound.org clips under a compatible license) or a small set Seth records/picks himself. Flagging this explicitly since it's the one part of this plan that isn't a pure code decision.

New file: src/js/behaviors/sound.js

Per CLAUDE.md's "Compartmentalized" and "No duplicate behavior" principles, this is a new shared behavior file, not logic bolted onto game.js or individual entity files:

const SOUND_KEY = 'tamofishi-sound-enabled';
let soundEnabled = localStorage.getItem(SOUND_KEY) === 'true';

const CLIPS = {
  feed: new Audio('assets/sfx/feed.wav'),
  eat: new Audio('assets/sfx/eat.wav'),
  death: new Audio('assets/sfx/death.wav'),
  murder: new Audio('assets/sfx/murder.wav'),
  spawn: new Audio('assets/sfx/spawn.wav'),
  toggle: new Audio('assets/sfx/toggle.wav'),
};

const playSound = (name) => {
  if (!soundEnabled) return;
  const clip = CLIPS[name];
  if (!clip) return;
  clip.cloneNode().play().catch(() => {}); // autoplay-policy rejections are fine to swallow
};

const setSoundEnabled = (on) => {
  soundEnabled = on;
  localStorage.setItem(SOUND_KEY, String(on));
  if (on) playSound('toggle');
};

const isSoundEnabled = () => soundEnabled;

Persisted the same way the murder-mode/prune-mode toggles and tank state already are — a dedicated localStorage key, following storage.js's existing try/catch-swallow pattern for storage access rather than introducing a new persistence mechanism.

UI: settings modal toggle

A new button in #settings-modal (index.html), next to murder-btn/prune-btn, following the same pattern — text flips between two states on click, exactly like MURDER/STOP MURDER: 

<button id="sound-btn" class="btn btn-modal">SOUND: OFF</button>
document.getElementById('sound-btn').addEventListener('click', () => {
  setSoundEnabled(!isSoundEnabled());
  document.getElementById('sound-btn').textContent = isSoundEnabled() ? 'SOUND: ON' : 'SOUND: OFF';
});
// set initial label from the persisted value on load, same as murder/prune do

Call sites to wire up

One line each, at the existing event, no control-flow changes:

  • game.js feedAt() → playSound('feed')
  • fish.js fed() and the shrimp-eaten branch → playSound('eat')
  • fish.js startDying() → playSound('death')
  • game.js's murder-cursor kill branch in handleTap() → playSound('murder')
  • fish.js's reproduction branch → playSound('spawn')

sound.js needs a <script> tag in index.html, loaded before game.js and any entity file that calls playSound — same ordering rule the existing behaviors/*.js scripts already follow.

Testing

playSound/setSoundEnabled/isSoundEnabled are pure enough to unit-test the same way mortality.js/feeding.js are tested today (via the existing vm.runInContext harness in __tests__/) — mock Audio and localStorage, assert playSound is a no-op when disabled, plays the right clip name when enabled, and that setSoundEnabled persists correctly. Actual audio playback isn't something a test can meaningfully verify beyond that.

Not in this plan

  • A volume slider — a single on/off toggle matches the murder/prune pattern; can be added later if wanted.
  • Background/ambient music — only discrete event sounds are covered here.
  • Sourcing the actual audio clips (see the note above).
